Hugging Face 十一月十六日宣布更换语言模型推理的路由服务，开发者原来的调用代码可以继续用。新接入的 OpenRouter 会根据价格、速度和可靠性挑选提供商，第一次请求失败，还能在同一次调用里换一家重试。对调用方来说，少处理一次报错当然方便。但同一份提示词会交给谁，也随着这次改动发生了变化。[Hugging Face 合作公告](https://huggingface.co/blog/openrouter)

读完公告，我停在了自带密钥的变化上。语言模型请求今后由 Hugging Face 账户或组织统一计费，原先自带提供商 API key 的方式不再支持。用户仍可指定提供商，或在设置里关闭某些提供商。图像、视频和音频请求则继续走原来的路径。代码可以不动，接收数据的服务和账户关系已经需要重新核对。

模型的名字在这里容易让人误会。选中一个开放权重模型，不等于把内容直接发给训练它的公司，也不等于自己运行模型。入口平台接收请求，路由服务决定交给哪家推理商，推理商再处理输入。默认重试给了系统更多完成任务的机会，也使开发者需要知道备用服务是否符合原有的数据要求。

这种要求不能只靠一个模型名称表达。十一月十九日，安全公司 Dragos 公布了一项持续数月的调查。研究者在约两百万次请求中放入独有链接和受控凭据，随后观察有没有系统访问这些内容。他们报告了提供商遭入侵、转售商读取提示词，以及数据处理未遵循声明等不同问题。测试从七月持续到十一月，结果不能换算成整个行业的泄露率。[Dragos 原始研究](https://www.dragos.com/blog/ai-supply-chain-security-canary-tokens)

这些用于追踪的内容被访问，可以帮助研究者找回对应的测试请求，却不能单凭一次触发就确定哪家公司泄露了数据。Dragos 还做了请求路径探测，尝试辨认中间经过的服务。一个入口返回成功，说明它交回了结果；数据途中经过谁，仍需要另一组记录回答。

十一月二十二日，OpenRouter 公告称已下架三家提供商，并取消一百二十五个端点的零数据留存资格。其中包括预防性移除，不能把这个数字理解成一百二十五个端点均已证实泄露。平台同时表示，研究没有显示 OpenRouter 自身遭到入侵或未经授权的访问，并称正在核验网络路径，检查请求和回复是否被转发给第三方。[OpenRouter 处置公告](https://openrouter.ai/blog/announcements/data-processing-incidents-on-inference-providers/)

Together 的说明把其中一种风险讲得更具体。公司十一月二十一日披露，部分六月、七月的推理请求样本被用于软件测试，保存在私有 Hugging Face 仓库。按公司说法，一个 AI 编码智能体把访问凭据提交到了公开代码仓库，未获授权的人据此下载了样本。公司仍在审查受影响内容。这是旧请求样本的新披露，不能与十一月的路由合作拼成一条因果链。[Together 事故说明](https://www.together.ai/blog/security-event-prompt-leakage-for-requests-in-june-and-july-of-2026/)

这起事件也解释了为什么需要问清留存。推理请求结束以后，样本还可能存在于测试流程中。它后来会受哪些系统、凭据和开发操作影响，取决于服务商怎样保存和使用它。只问模型有没有拿这些内容训练，还没有问到这里。

OpenRouter 的现行文档就把训练用途与留存分开。Safety Retention 允许服务为防止滥用保存请求和回复，同时声明不用来训练。OpenRouter 对零数据留存的定义是处理完成后不做常规存储，其公布的政策更新还将疑似儿童性虐待材料的审查、报告和依法保存列为例外。阅读隐私承诺时，需要看它限制的是哪一种用途，以及例外适用于哪些请求。[提供商数据政策](https://openrouter.ai/docs/guides/privacy/provider-logging)、[零数据留存说明](https://openrouter.ai/docs/guides/features/zdr)

具体设置也得跟着入口核对。OpenRouter 当前文档说明，请求中的零留存参数仍受账户是否允许 Safety Retention 的选择影响，不能把一个参数当作无条件保证。Hugging Face 公告给出的是它自己的提供商开关，不能据此认定用户在 OpenRouter 网站上的设置会自动约束 Hugging Face token 发出的请求。两套账户之间如何传递限制，需要对应产品明确说明。

平台自身的日志还要另看。OpenRouter 表示，输入输出日志与供平台改进产品的内容使用默认关闭，但用户可以启用，另有安全相关例外。平台也会保留请求的 token 数、延迟等元数据。开发者排查路由需要这些记录，却未必需要把客户的完整提示词再复制到自己的调试日志里。[OpenRouter 数据收集说明](https://openrouter.ai/docs/guides/privacy/data-collection)

统一路由的便利仍然成立。模型多、提供商多，开发者可以少维护几套调用和计费逻辑。我更愿意把数据去向也放进这份便利的交付要求里。Hugging Face 已提供按实际提供商查看用量和关闭提供商的功能；OpenRouter 在本次处置中表示正在核验转发路径，并在恢复零留存资格前要求验证。这些功能和处置，才让用户有机会核对服务声明是否仍然适用于自己的请求。

对要发送客户资料或内部代码的团队，选型时可以先缩小允许接收数据的提供商范围，再检查失败重试会去哪里、各端点适用什么留存规则。缩小范围可能牺牲价格或可用性，需要结合业务接受的代价决定。等到下一次路由或政策变更，负责人应当能从记录里找出受影响的调用，再判断是否继续发送。那份记录里，只有模型名称还不够。
